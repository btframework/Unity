# Serial Framework — Unity Examples

A collection of Unity example projects demonstrating the **[Serial Framework](https://www.btframework.com/serialframework.htm)**. Each example focuses on a specific area of the framework — opening and driving a serial port, discovering serial and USB hardware, and transferring files over a serial transport using the OBEX Object Push Profile.

The examples share a common structure: the runtime logic lives in a `MonoBehaviour`, and the entire user interface is generated by an editor script. There are no hand-authored scenes or prefabs to maintain, so the samples stay aligned with the framework API and rebuild cleanly on any machine.

## Examples

| Example | Focus | Key framework classes | Reference documentation |
|---------|-------|-----------------------|-------------------------|
| [Serial Client](./SerialClient/README.md) | Open a serial port, configure it, exchange data, handle modem events | `wclSerialClient`, `wclSerialMonitor` | [serialclient.htm](https://www.btframework.com/serialclient.htm) |
| [Serial Monitor](./SerialMonitor/README.md) | Enumerate serial and USB devices, track hot-plug events, enable/disable USB devices | `wclSerialMonitor` | [serialmonitor.htm](https://www.btframework.com/serialmonitor.htm) |
| [Serial OPP Client](./SerialOPPClient/README.md) | Push a file to a remote peer using OBEX Object Push over a serial transport | `wclSerialClient`, `wclObexOppClient` | [obex.htm](https://www.btframework.com/obex.htm) |
| [Serial OPP Server](./SerialOPPServer/README.md) | Receive files from a remote peer using OBEX Object Push over a serial transport | `wclSerialClient`, `wclObexOppServer` | [obex.htm](https://www.btframework.com/obex.htm) |

Each example folder contains its own `README.md` with setup instructions, a description of the user interface, behavioural notes, and platform considerations.

---

## How the examples relate

The four examples cover the two halves of a serial application — device discovery and data exchange — and then apply them to a file-transfer protocol:

- **Serial Monitor** is the discovery layer. It demonstrates how to list serial ports and USB devices, how to react to hardware changes, and how to control the driver state of a USB device on Windows.
- **Serial Client** is the transport layer. It demonstrates how to open a port returned by the monitor, read and write its configuration, timeouts and buffer sizes, drive the control lines, and send and receive data.
- **Serial OPP Client** and **Serial OPP Server** sit on top of the transport. They run the OBEX Object Push Profile over a `wclSerialClient` connection, showing how a higher-level protocol can be layered on top of the same serial byte stream that the Serial Client example uses directly.

A typical workflow reuses the pieces in this order: enumerate devices with the monitor, connect to one with the client, then either exchange raw bytes or hand the connection to an OBEX session.

## Requirements

- **Unity** 2021.3 LTS or newer (TextMeshPro and the Unity Editor API are used)
- **Serial Framework** installed and referenced by every example project
  - Product page: https://www.btframework.com/serialframework.htm
  - Installation guide: https://www.btframework.com/howtoinstall.htm
- **Platforms:** Windows and macOS
  - Serial enumeration and serial communication work on both platforms
  - USB enumeration and USB enable/disable are Windows-only
- Both **Mono** and **IL2CPP** scripting backends are supported without additional configuration

## Common setup

Every example follows the same three-step setup.

### 1. Install the Serial Framework

Add the Serial Framework assemblies (`wclCommon`, `wclCommunication`, `wclSerialFramework`, and their dependencies) to the Unity project and make sure they are referenced by the assembly that contains the example's `MonoBehaviour`. The set of assemblies required depends on the example:

- **Serial Client** and **Serial Monitor** use `wclCommon` and `wclSerialFramework`.
- **Serial OPP Client** and **Serial OPP Server** additionally use `wclCommunication`, which provides the OBEX client and server types.

### 2. Build the scene

Each example ships with an editor script that constructs the entire user interface. Open the scene you want to try and use the corresponding menu entry:

| Example | Menu entry |
|---------|------------|
| Serial Client | **Tools → Serial Client → Build Scene** |
| Serial Monitor | **Tools → Serial Monitor → Build Scene** |
| Serial OPP Client | **Tools → Serial OPP Client → Build Scene** |
| Serial OPP Server | **Tools → Serial OPP Server → Build Scene** |

The builder creates the canvas and controls, adds the demo `GameObject`, wires the UI fields, generates the row prefabs under `Assets/Prefabs`, and saves the active scene. If Unity does not save the scene automatically, save it manually (`Ctrl+S` / `Cmd+S`) before building the player — the editor logs a warning in that case.

### 3. Run the scene

Enter Play mode and use the controls described in the example's own `README.md`. The examples that connect to a port expect a real serial device or a virtual serial port pair, and the OPP examples additionally require a peer that speaks OBEX Object Push over the serial transport.

## Repository layout

Each example is self-contained and follows the same internal layout:

```
<Example>/
├── README.md                        # Example-specific documentation
├── Scripts/
│   ├── <Example>SceneBuilder.cs     # Editor: builds the scene
│   └── <Example>Demo.cs             # Runtime: all demo logic
├── Scenes/
│   └── <scene>                      # Created by the scene builder
└── Prefabs/
    └── <Example>Row.prefab          # Created by the scene builder
```

Folder names are indicative; the exact paths depend on how the projects are imported into Unity. The scene builder scripts are wrapped in `#if UNITY_EDITOR` and have no runtime footprint. The demo scripts are plain `MonoBehaviour` classes that use only the public Serial Framework API.

### Shared components

All examples use a common `TableRowUI` component for log and table rows. It is responsible for populating cells, applying the normal or selected background, and forwarding clicks. The component is part of the demo project rather than the framework, and it is reused unchanged by the Serial Client, Serial Monitor, Serial OPP Client, and Serial OPP Server scene builders.

## Platform notes

### Windows

- Serial device names are short identifiers such as `COM1` and `COM4`.
- USB enumeration and USB enable/disable are available. Both operations require the application to run elevated.
- Any message-processing method is acceptable when calling `wclSerialClient.Connect`.

### macOS

- Serial device names are full node paths such as `/dev/cu.usbserial-1420`.
- When calling `wclSerialClient.Connect`, use `wclMessageProcessingMethod.mpAsync` so events are delivered on a worker thread.
- USB enumeration and USB enable/disable are Windows-specific and return an error on macOS. The Serial Monitor example remains functional for serial devices.
- The rest of the API — configuration, timeouts, buffers, events, `Write`, `PurgeComm`, `EscapeCommFunction`, and the OBEX client and server — behaves identically to Windows.

The macOS-specific `Connect` pattern is documented in the **Cross-platform notes: macOS** section of the Serial Client reference page.
